# OSUZ — исправления Product JSON-LD для Google Search Console

Дата: 14.10.2026. Основа: присланный архив `Osuz (6).zip`.

## Исправлено непосредственно в статическом проекте

Файл: `product.html`.

1. `sku`: строка должна быть настоящим артикулом **без пробелов / управляющих символов**. Если исходный `order_code` не соответствует требованиям Google, поле `sku` не публикуется — код товара остаётся видимым пользователю в карточке.
2. `gtin8/12/13/14`: публикуются только штрихкоды соответствующей длины с корректной контрольной цифрой, сохраняются ведущие нули. Придуманный GTIN не подставляется.
3. `brand`: указывается реальный производитель, если он известен. `Без бренда` / `No brand` не выдаются за фирму-производителя.
4. `availability`: если `require_stock_for_cart=1`, статус формируется из `total_stock`; если `require_stock_for_cart=0`, продавец подтверждает наличие вручную, поэтому статус **не угадывается**. Закрытый магазин тоже не означает `OutOfStock`.
5. Один продавец с ценой → реальный `Offer`, несколько продавцов → `AggregateOffer` (страница сравнения предложений). Цена берётся из `product_listings.price`, а не из общей устаревшей цены товара.
6. Данные с сервера не затираются во время первоначальной загрузки; браузер пересоздаёт Product JSON-LD только после успешной загрузки предложений продавцов.
7. Если активных предложений с действительной ценой нет, не публикуется выдуманная цена или наличие.

## ВАЖНО: откуда берутся предупреждения в Search Console

На боевом сайте ЧПУ-страницы вида `/product/<slug>-<id>` обрабатываются **бэкендом** (см. `DEPLOY_NOTES.txt` в архиве). Он создаёт HTML/JSON-LD в `backend_osuz/routes/seo.js`. Этого файла **нет** в предоставленном архиве. Изменение одного только `product.html` **не гарантирует**, что Google перестанет видеть проблемы в исходном HTML, выданном сервером.

В `tools/seo-product-schema-server.cjs` подготовлен отдельно протестированный помощник для бэкенда (CommonJS), но он НЕ подключён к отсутствующему серверу. Разработчику бэкенда надо интегрировать его в реальный `routes/seo.js`, подставляя реальные `product`, `listings`, публичный `url`, изображения и описание.

Пример вызова внутри существующего серверного маршрута (пример, не готовая замена маршрута):

```js
const { buildProductSchema } = require('./path/to/seo-product-schema-server.cjs');
const schema = buildProductSchema({
  product,             // реальная карточка из БД
  listings,            // реальные продавцы и product_listings.price / stock
  url: canonicalUrl,   // абсолютный https://osuz.uz/product/...
  images: imageUrls,   // реальные публичные HTTPS URL картинок
  description: productDescription
});
// Вставлять только если schema !== null. В HTML экранировать символ < в JSON.
const jsonld = schema ? JSON.stringify(schema).replace(/</g, '\\u003c') : null;
```

Не должно одновременно оставаться двух противоречивых Product JSON-LD на одной странице. При формировании HTML на сервере поле `sku` и доступность продавца надо валидировать **до выдачи HTML поисковому роботу**.

## Что ещё требуется от реальных данных / политики магазина

- `hasMerchantReturnPolicy`: нужно знать правила возврата (разрешён ли возврат, сроки, стоимость, способы). На сайте есть `terms.html`, но он не доказывает единый срок или условия возврата товаров у разных продавцов. Не следует выдумывать возврат за 14/30 дней или отмечать `MerchantReturnNotPermitted`, если это не установлено фактически.
- `shippingDetails`: `deliveryEnabled=true` ещё не сообщает стоимость доставки, географию и сроки. Для `OfferShippingDetails` нужна достоверная цена, валюта `UZS`, зона доставки и при необходимости сроки. **Нельзя объявлять бесплатную доставку или фиксированную стоимость, если её нет в API/политике**.
- Глобальный идентификатор: GTIN или подлинная марка + артикул производителя (MPN). Если товар действительно без бренда/GTIN, проблема может остаться рекомендательной. Не подставляйте название маркетплейса как бренд самого изделия.
- Если условия доставки/возврата общие для бизнеса, Google допускает задать их на уровне `Organization`/настроек Merchant Center, но только по действительной политике. Для маркетплейса условия могут отличаться между продавцами.

Google: https://developers.google.com/search/docs/appearance/structured-data/merchant-listing
Google (агрегаторы): https://developers.google.com/search/docs/appearance/structured-data/product-snippet

## После деплоя

1. Обновить и статические HTML, и сборку `backend_osuz` — если backend копирует HTML в Docker/сборку.
2. Открыть реальную страницу `/product/...` и сравнить JSON-LD в «Просмотр кода страницы» (HTML с сервера) и в инспекторе DOM (после загрузки JS). Проверить, что нет старого неправильного Product JSON-LD.
3. Проверить конкретные проблемные URL в https://search.google.com/test/rich-results и в Google Search Console → Проверка URL → Проверить опубликованную страницу.
4. Только после исправления боевого сайта нажать «Проверить исправление». Повторный обход Google может занять несколько дней.

## Проверено локально

- Синтаксис основного JavaScript и серверного helper.
- Случаи: валидный/невалидный SKU, валидный/невалидный GTIN, настоящее/неизвестное наличие, один/несколько продавцов, отсутствие выдуманной политики доставки/возврата.
- НЕ проверялось: подключение к боевой базе, существующий код backend `routes/seo.js`, реальные URL из отчёта Google, серверный рендеринг и повторный обход Google.
